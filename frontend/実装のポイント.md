# 初心者向け：今回の実装のポイント

今回できるようになったのは、「データベースのタスクを検索して、ブラウザにカードとして並べること」です。画面にサンプルを直接書いたものではなく、バックエンドの検索結果を表示しています。

この文書はフロントエンドの設計意図を説明します。バックエンドを含む全体の流れと技術の役割は[学習メモ](../学習メモ.md)、起動・テスト手順は[フロントエンドREADME](README.md)を参照してください。

## 1. 画面とデータ取得を分ける

検索したときの流れは次のとおりです。

```text
利用者が「API」と入力して検索
  → Appが検索条件を確定
  → useTasksが取得処理を開始
  → fetchTasksが /api/tasks?q=API へGETリクエスト
  → ViteがSpring Bootへ転送
  → バックエンドがPostgreSQLを検索
  → JSON配列が返る
  → TaskBoardが進捗ごとに分ける
  → TaskCardが1件ずつ表示
```

フロントエンドは「見せ方」、バックエンドは「検索とDBアクセス」を担当します。ブラウザからDBへ直接接続しないので、DBのパスワードを画面のコードに書く必要がありません。

## 2. Reactのコンポーネントは画面の部品

`App`は画面全体、`TaskBoard`は3列のボード、`TaskCard`はカード1枚の部品です。同じカード用コードへ異なるタスクを渡すことで、一覧を作れます。

例えば、期限の見せ方を直したいときは`TaskCard.tsx`を確認します。検索用URLを直したいときは`api/tasks.ts`を確認します。役割を分けることで変更箇所を見つけやすくしています。

## 3. 入力中の条件と、検索済みの条件は別

`App.tsx`の`draft`は入力途中の値、`conditions`は最後に検索を実行した条件です。

「API」で検索した後、入力を「画面」に書き換えただけなら、ボードにはまだ「API」の結果が表示されています。検索ボタンを押すと条件と結果を更新します。画面には適用中の条件を表示するので、何の結果かを確認できます。

「再取得」は適用中の条件でやり直す操作です。「クリア」は入力と条件を両方戻し、全件を取得します。

## 4. TypeScriptの型はデータの約束

`types.ts`でタスクの形を定義しています。例えば、ステータスは`todo / doing / done`、期限は文字列または`null`です。

この約束によって、存在しない項目名や誤った値をコードに書いたときに気づきやすくなります。ただし、TypeScriptだけで実際のAPI応答まで保証できるわけではありません。`api/tasks.ts`でもレスポンスの主要な項目・値を確認し、不正な形式を受け取ったらエラーを表示します。

## 5. 検索語はURL用に変換する

日本語や`&`、`%`などを単純にURLへつなぐと、検索条件の区切りと混同することがあります。そこで`URLSearchParams`を使い、安全にクエリ文字列を作ります。

「すべて」を選んだ場合は`status`を送りません。既存APIでは空文字の`status`は400エラーになるためです。前後の空白だけを除き、検索語そのものはAPIへ渡します。

## 6. 通信には待ち時間と失敗がある

API呼び出しはすぐ終わるとは限りません。画面は「読み込み中」「取得成功」「取得失敗」を区別します。失敗したときに0件と表示するとタスクが消えたように見えてしまうため、全体には取得失敗のメッセージ、各列の件数には「—」を表示します。

検索を続けて実行すると、古い検索の結果が後から届くこともあります。`AbortController`で前の通信を中断し、さらに有効な通信かどうかを確認してから結果を反映します。これで古い結果による上書きを防ぎます。10秒待っても応答がない場合はタイムアウトを表示し、再取得できるようにしています。

## 7. 3列に分けてもAPIの並び順を保つ

APIはステータス・`sortOrder`・UUIDの順に整列して返します。初期表示では`filter`で各列のタスクを取り出し、その順序を維持します。ソートボタンを選択すると、その列の取得済みデータだけを優先度・期限で並べ替えます。期限なしは常に最後、同順位は直前の表示順を維持します。選択中のソートは検索・再取得後も適用しますが、画面を再読み込みすると解除されます。DBへの保存はしません。

期限の`YYYY-MM-DD`は時刻を持たない日付です。UTCの日時へ変換せず表示することで、タイムゾーンによって前日にずれる問題を避けます。期限超過は利用者の端末の今日の日付と比較し、完了タスクは強調しません。

## 8. テストは「代役で確認」と「実物で確認」の両方

自動テストではAPIの代役を用意し、成功・0件・失敗・遅い応答などを再現します。毎回DBを操作せず、同じ条件で確認できるのが利点です。特に通信の順番が逆になるケースや10秒のタイムアウトは、自動テストで再現しています。

一方、代役だけでは接続設定の間違いを見つけられません。そのため、実際にPostgreSQL・Spring Boot・Viteを起動して、Chromeから検索した結果が表示されることも確認しました。

`npm run typecheck`は型の間違い、`npm run lint`はコードの規則、`npm run build`は配布用ファイルへの変換、`npm test`は期待する動作を確認します。それぞれ確認する対象が異なります。

詳細モーダルも一覧APIで取得済みのデータを使います。カード選択のたびに詳細APIを呼び出す構成ではありません。

## 次に実装するときの土台

追加・更新・削除はapi/tasks.tsで通信を扱い、画面ではそれぞれの成功・失敗に応じて表示を更新します。DeleteTaskConfirmは送信中の二重操作を防ぎ、失敗時にはチェック状態と確認画面を保持します。「今後この確認を表示しない」の選択は削除要求に含め、DBで一括保存します。Appは削除ボタンを押すたびに最新設定を取得し、確認が不要なら直接削除を要求します。

## デモと画面をそろえた変更

画面部品の配置と余白は、合意済みデモのCSSを引き継ぐ構成に変更しました。追加ボタンは見出しの右側、優先度と期限の昇降順ボタンは各列の見出しの下に置いています。検索フォームはボード下の折りたたみへ移し、ボードを押し下げないようにしました。

カードを押すと、取得済みのデータを詳細モーダルへ表示します。各列の並べ替えは画面内だけで行います。タスク追加はPOST APIで保存します。編集・移動もAPIで保存できます。削除はDeleteTaskConfirmで確認し、DELETE APIの204応答後に一覧を再取得します。物理削除のため復元できません。デモと外観をそろえることと、APIが対応していない保存操作を実行することは別々に扱っています。

その後の依頼により、元のプロジェクト内の `frontend/` へ実装を移し、追加ワークツリーを解除しました。現在は通常の作業ブランチで管理しています。ボタン・並べ替え・モーダルのテストも追加し、全41件と型チェック・Lint・ビルドの成功を確認しました。

## 新規登録の流れ（Issue #11）

追加フォーム → FetchでPOST /api/tasksへJSON送信 → Controller → Serviceで入力確認・未着手末尾の採番 → Repositoryで保存 → PostgreSQLへコミット → 201 Created → フォームを閉じ、検索条件を解除して一覧を再取得、の順に処理します。DBに保存するので画面を再読み込みしても新しいタスクを取得できます。列の優先度・期限ソート条件の永続化は別作業です。

編集とドラッグ移動の現在の操作・制限は[フロントエンドREADME](README.md)、PUT・PATCHの仕様は[バックエンドREADME](../backend/README.md)を参照してください。
