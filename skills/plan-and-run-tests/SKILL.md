# 項目を確認してからテスト

作業場所がRaiseTech_TaskManagerであることを確認し、リポジトリルートを特定する。編集や実行の前に、そのルートの `AGENTS.md` と `テスト運用ルール.md` を必ず読んで従う。ルールを読めない場合は推測で進めず、場所を調べ、見つからなければ理由を報告する。

変更した仕様・コード・既存テストを読み、対象・操作条件・期待結果・方法・既存/追加/省略の理由・優先度を表にする。ルールの観点から不足をレビューし、高優先度の不足を埋めてから実行する。利用者の明示要求がなければ承認待ちにしない。未変更の独立範囲は省略理由を残す。結果・未確認・省略・残るリスクはIssue・PRと報告へ記載し、READMEへ件数履歴を追加しない。

既存のIssue・ブランチと未コミット変更を確認し、worktreeは使わない。コミット・push・PRは明示的な依頼がある場合のみ行う。

## 実行前の照合と独立レビュー

ルール第5〜7章に従い、実行前に前回のIssue/PRコメントと結果を取得し、項目IDごとに前回成功時点と今回の差分・依存箇所・環境条件を照合する。「前回結果を根拠に使わない」として照合を省略しない。未コミット作業はコミットIDだけで同一状態と判断しない。

次の表を計画に追加し、実行対象と省略対象を決めてからコマンドを組み立てる。

| 項目ID | 前回結果の参照・検証状態 | 今回変わった依存箇所・条件 | 実行/省略/未確認と理由 | 実行コマンド・作業場所 |
|---|---|---|---|---|

変更した共通部品を通る項目は、テストファイル自体に差分がなくても再実行を検討する。一方、前回成功後に必要な依存箇所・条件が変わっていない独立項目は、利用者が全件実行を指定した場合を除き省略する。過去の記録が不十分なら不足を明記し、今回の変更と依存関係から必要範囲を再検証する。記録不足だけを理由に全件実行へ広げない。ファイル・テスト名で選択し、全件実行が必要なら影響範囲を絞れない具体的理由か利用者の全件指定を記録する。

コマンドの作業場所・対象の存在・パッケージスクリプトの内包処理も確認する。buildが同じ型チェックを含む場合など、同一状態での重複実行を避ける。テスト名と書式は既存の構成に合わせる。

項目表を作ったら、利用可能なサブエージェント1名に仕様・差分・テストを渡し、読み取り専用の独立レビューを依頼する。編集・DB操作・テスト実行・外部送信は委任しない。不足だけでなく、不要な再実行・省略根拠・コマンドと項目の対応もレビュー対象とする。指摘の採否は主担当が判断する。利用できない場合は自己レビューと独立レビュー未実施を記録する。

DBを使う場合は第6章を必ず適用する。DB分離は今回の方針に含めない。実接続先のホスト・ポート・DB・スキーマ、変更テーブル・行・波及範囲・後片付けを確認し、資格情報を出力しない。既存データの保全が確認できない書き込みテストは始めない。

## 失敗時の修正・再実行

ルール第8章に従い、固定回数上限を設けず、原因・証拠に基づいて必要な検証を継続する。各再実行前に失敗分類、エラー要約、原因と根拠、実装/テスト/環境の変更内容、次の仮説、再実行範囲を記録する。同じ失敗を根拠なく繰り返さず、新しい証拠が得られなければ追加調査・レビューへ進む。期待値を緩めない。

修正後は照合表を更新して影響する項目と必要な回帰だけを選ぶ。計画・期待結果・影響範囲を大きく変える場合は再レビューし、主担当が採否理由を記録する。権限・仕様・外部状態で進められない項目は阻害要因と再開条件を明記して保留し、独立項目は続ける。保留を完了にしない。

## 画面の完了条件

ルール第9章に従い、計画に画面表示・主要操作・再読み込み・失敗時保全の期待結果と方法を含める。白画面や主要操作不能を観測したら切り分けと再確認を行い、ビルド成功/HTTP 200で代替しない。ツール障害とアプリ障害を断定せず、重要経路の未確認や異常が残る場合は検証未完了として報告する。

## 結果を次回へ引き継ぐ

既存のIssue・PRと作業報告に項目ID、実行コマンドと作業場所、成功/失敗/省略/未確認、対象コミットと未コミット変更の識別情報、必要な環境条件を残す。記録のためだけにPRを作成しない。未コミット変更は対象ファイルと関連差分のハッシュなど、次回に状態を照合できる情報を用いる。秘密を含む差分・環境情報の本文は送信しない。

DOM操作・モックAPI・実API/DB・実ブラウザ目視を分けて結果を書く。色・配置・ネイティブ操作はDOMテストだけで確認済みにしない。残った未確認事項と、再利用できる手順上の改善候補を報告する。スキル自身の更新は依頼範囲を確認して行い、この報告だけを理由に自動で書き換えない。

完了時・未完了時の報告にはルール第8章の履歴表を付ける。初回を試行1・修正ループ0、失敗後の原因分析・変更/新しい証拠・再実行の一連を1ループと数える。総ループ数（0回も明記）、初回の実装内容とエラー、各ループで何を実装/変更し、何がエラーで、何を再実行してどうなったかをIssue・PRとユーザー向け報告の両方に残す。

環境・ツールのためテスト開始前に実行不能だった場合も、原因を受けて条件を変え再実行すればループに含める。同じエラー文だけで同一原因と断定せず、新しい証拠・仮説・変更点を記録する。
