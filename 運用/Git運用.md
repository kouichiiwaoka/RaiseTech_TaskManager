# GitHubでの開発手順

Git操作・開発フロー・コミットとPRの記述・ブランチ整理のルールの正本は本書です。[CLAUDE.md](../CLAUDE.md) から読み込まれ、Claude Codeの作業にも適用されます。

## 許可する操作と禁止する操作

- 設定済みリモートへの通常のfetch・pull、Issue作成・閲覧・更新、PRの閲覧は個別確認なしで行ってよいです。Issue関連の外部送信は設定済みリモートの当該リポジトリ内に限ります。GitHub以外への送信は、[CLAUDE.md](../CLAUDE.md) の「AWSへのデプロイ」で許可した範囲に限ります。
- コミット・push・PR作成や更新・マージは、ユーザーの明示的な依頼がある場合に、依頼された範囲でだけ行います。コミットだけの依頼はpushやPR作成の許可を含みません。
- mainへの直接push・直接コミット・ローカルマージ結果のpushは禁止です。通常のマージは許可します。
- checkout / switch自体は禁止しません。実行前に差分と対象を確認し、未コミット変更・無関係な変更を破棄しません。
- 未コミット変更を破棄するhard reset、強制checkout、作業ツリーを破棄するrestore・`checkout -- <path>`、git clean、履歴改変（rebase、amendなど）は禁止です。
- .git・履歴・オブジェクト・参照・reflogの削除、履歴の初期化・全消去、filter-branch / filter-repo、reflog expire、update-ref -d、prune、gcによる復旧情報の除去は禁止です。
- force push（--force-with-lease、+refspec、--mirrorを含む）、未マージのリモートブランチ削除・タグ削除、未マージブランチの強制削除、stash drop / clearは禁止です。
- 送信前に送信先・対象ブランチ・差分を確認し、秘密情報・個人情報・無関係なファイルを含めません。
- 過去の英語コミットを書き換えるためのamend・rebase・force pushは行いません。

## 作業場所とブランチ

Git worktreeによる追加作業ツリーの作成・利用は禁止です。Claude Codeを含め、元のプロジェクトディレクトリで作業ブランチを切り替えて作業します。未コミット変更は破棄せず、切り替え前に差分を確認して保全します（必要なら対象を限定した `git stash push`）。作業の分離を理由に別worktreeを作成しません。

ブランチ名は `<type>/<issue番号>-<英小文字のkebab-case>` とします。typeはfeature、fix、refactor、docs、test、choreのいずれかです（例: `feature/123-task-filter`）。1ブランチ・1PRは1つの主Issueを扱います。

## 作業開始からPR作成まで

調査のみの場合を除き、機能追加・修正・リファクタリング・文書・設定変更のすべてで、編集前に次の手順を守ります。

1. 作業ツリーの状態・差分・現在のブランチを確認します。既存の変更を勝手に破棄しません。main上では編集・コミットしません。
2. 目的と完了条件が一致する未完了Issueを確認します。なければ目的・対象範囲・完了条件・確認方法を記載して作成します。重複Issueは作りません。秘密情報・個人情報・非公開ログは含めません。
3. fetchして最新の `origin/main` を確認し、`docs/7-japanese-git-descriptions` のようにIssue番号を含む作業ブランチを作成します。既存の未コミット変更を引き継ぐ場合も、保全したままIssueに対応する作業ブランチへ移してから編集を続けます。
4. 実装や文書変更を行い、変更に適したテスト・確認を実施します。
5. 差分を確認して、ローカルの未コミット変更と確認結果を報告します。通常の作業依頼ではここで止め、作業が終わったことを理由にコミット・push・PR作成を自動実行しません。
6. ユーザーからコミットを依頼された場合に限り、ステージ対象を確認し、秘密情報・個人情報・無関係な変更を含めずにコミットします。
7. pushを依頼された場合に限り、送信先と対象ブランチを確認し、作業ブランチを明示してpushします（例: `git push -u origin <作業ブランチ>`）。
8. PR作成を依頼された場合に限り、mainを統合先とするPRを作成します。本文には `Closes #<issue番号>`、変更内容、確認結果、未確認事項を書きます。

同じ目的の関連修正は既存Issue・作業ブランチでまとめ、小さな作業ごとにコミットやPRを増やしません。

未マージPRへの同じIssueの追加修正は、対応する作業ブランチで編集・確認し、ユーザーに依頼された場合にコミット・pushします。既存PRの差分は更新されるため、PRの説明も最終的な内容に合わせます。マージ済みの場合は別Issue・別ブランチ・別PRで対応します。

Issue作成・確認、ブランチ作成、push、PR、保護設定が権限や接続の問題でできない場合は、必須手順を省略して実装・統合を続けません。状況と再開に必要な操作を報告します。保護の解除や迂回を代替策にしません。GitHub側の保護設定変更はこの運用を強化する範囲で許可し、新しい課金・権限付与・保護の弱体化は行いません。

## 日本語での説明

コミットの件名・本文、PRのタイトル・本文、マージ時に指定するコミットの件名・本文は日本語にします。Conventional Commitsの接頭辞（`feat:` / `fix:` / `refactor:` / `docs:` など）、API名・コード識別子・コマンド・URL、`Closes #<issue番号>` はそのまま使用できます。接頭辞に続く変更の説明は日本語にします。ブランチ名は英小文字のkebab-caseを維持します。

コミット件名の例：

```text
refactor: タスク取得処理をサービス層へ分離する
```

コミット本文を付ける場合も、変更理由や確認内容を日本語で記載します。

PRタイトルの例：

```text
feat: PostgreSQLのタスクREAD APIを実装する
```

PR本文の例：

```markdown
## 変更内容
タスク一覧・検索・詳細取得のAPIを追加します。

## 確認結果
実PostgreSQLへのHTTP統合テストとビルドが成功しました。

## 未確認事項
別端末での実行は未確認です。

Closes #5
```

過去の英語コミットは書き換えません。新規コミットと、今後作成・更新するPRの説明に適用します。

## マージとブランチの整理

mainへの統合はPR経由です。ユーザーからマージを依頼された場合に限り、必須チェック成功・会話解決・差分確認後にマージします。他者の承認は必須にしませんが、依頼されたレビューは尊重します。

mainなどの統合先へマージ済みの作業ブランチは、ローカル・設定済みリモートとも個別確認なしで削除してよいです。削除前にfetchし、最新コミットが統合先の祖先であることを `git merge-base --is-ancestor` で確認します。未送信コミットがなく、別worktreeでも使用していないことを確認します。main・デフォルト・保護ブランチは削除しません。

条件を満たした作業ブランチに限り、ローカルは `git branch -d <branch>`（`-D` や `--delete --force` は使わない）、リモートは `git push origin --delete <branch>` を使用します。未マージのブランチや確認できないブランチは残して報告します。Claude Codeの設定とフックではマージ済みかを判定できないため、リモート削除は確認（ask）になります。これは未マージブランチ削除の許可ではありません。
