# 文書運用ルール

## 作成・編集前に確認すること

文書の作成・編集時は、先に本書とCLAUDE.mdを読む。対象読者、文書の役割、情報の正本、実装との差分を確認する。文書更新だけの依頼でも既存Issue・作業ブランチのルールに従い、mainでは編集しない。

## 情報を置く場所

| 場所 | 書く内容 | 原則書かない内容 |
|---|---|---|
| ルートREADME | 現在の機能、環境、起動・停止・テスト手順、利用上の制限、関連文書への入口 | Issue別の作業履歴、成功件数、確認ツールの失敗談 |
| frontend/backendのREADME | 各領域の操作・API仕様・設定・検証の実行方法 | 同じ手順の別表現、日ごとの実行結果 |
| 要件・機能仕様・受入条件 | 目標要件、操作ルール、満たすべき条件、現在と予定の区別 | 合格したかの実行履歴、作業日報 |
| 設計書・技術構成書 | 実際の構造、制約、バージョン、現在の選定・維持理由、未決定事項 | 根拠のない選定理由、検証結果の羅列 |
| 学習メモ・実装のポイント | 仕組み、技術の役割、具体例、コードとの対応 | Issueごとの経緯や一時的な実行環境の事情 |
| `運用/` | 作業のルール（Git・テスト・文書）、デプロイなどの手順書、作業の記録 | 要件・設計の内容（設計書はルート直下に置く） |
| Issue・PR | 作業範囲、判断理由、テスト計画・実施結果、未確認・失敗・省略理由 | 秘密情報、個人情報、不要なログ全文 |
| スキル（`.claude/skills/`） | 繰り返す作業の判断基準・手順、参照すべき正本 | 実行結果、正本の大量コピー |

バージョンは設定ファイル・ロックファイルを正とし、採用理由は技術構成書に集約する。操作は領域別README、全体の入口はルートREADMEとする。重複が必要な起動コマンドなどは正本と照合する。

## 書き方と更新の原則

- 現在使える機能、将来の要件、過去の検証を混同しない。未実装を実装済みとして書かない。
- 利用者に影響する制限はREADMEへ書く。操作ツールが使えなかった事情や一度のテスト成功件数はIssue・PRに記録する。
- 「Issue #13の確認結果」のような作業別の章を恒久文書へ追加しない。機能説明は「タスクの編集」など読者の目的を見出しにする。
- READMEの既存の結果履歴は、新たな編集対象になった際に整理する。重要な未確認事項は消して成功扱いせず、必要なら元のIssue・PRへ記録して参照する。
- 技術上の判断理由は残す。後から調べた維持理由を、導入時に検討した理由として書かない。時点依存の情報には確認日と根拠を付ける。
- 要件の変更や受入条件の合格を、文書整理だけで勝手に決めない。関連IDを維持する。
- 認証情報、個人環境の絶対パス、非公開ログ全文は埋め込まない。例は架空の情報を使う。

## 編集後の確認

実装・他文書との整合性、参照リンク、図と本文の対応、コマンドの作業ディレクトリ・標準ポート、秘密情報、差分を確認する。文書だけの変更ではアプリの全テストを機械的に再実行しない。結果はIssue・PRまたは作業報告にまとめる。
